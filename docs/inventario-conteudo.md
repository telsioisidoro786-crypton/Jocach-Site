# Inventário de conteúdo — JOCACH Lda

**Versão:** 1.0  
**Data:** 19 de setembro de 2026  
**Âmbito:** Conteúdo institucional e página de serviços  
**Objetivo:** Validar os dados oficiais da JOCACH antes de atualizar os textos publicados no site.

## Como utilizar este documento

Este inventário separa o conteúdo que já está publicado do conteúdo que ainda precisa de confirmação. A equipa deve preencher os campos marcados como **A validar** antes da próxima edição do site. Quando uma decisão estiver confirmada, deve ser registada na coluna ou secção correspondente para evitar versões diferentes da mesma informação em páginas distintas.

A classificação usada neste documento é a seguinte:

- **Confirmar:** o dado aparece no site, mas precisa de validação por uma pessoa responsável.
- **Completar:** existe uma mensagem inicial, mas faltam detalhes comerciais ou operacionais.
- **Decidir:** é necessária uma escolha de posicionamento, tom ou prioridade.
- **Pronto para edição:** o conteúdo pode ser aproveitado, sujeito à revisão final de linguagem.

### 2.3 Perguntas comerciais para cada serviço

Antes de reescrever a página, deve ser recolhida a mesma informação para cada serviço:

1. **Para quem é este serviço?** Cliente particular, empresa, investidor, entidade pública ou outro.
2. **Qual é o problema que resolve?** A resposta deve ser concreta e compreensível para quem não é especialista.
3. **O que está incluído?** Listar entregáveis e limites do trabalho.
4. **O que não está incluído?** Indicar dependências, taxas, aprovações ou serviços de terceiros.
5. **Qual é o ponto de partida?** Documentos, terreno, briefing, levantamento ou reunião inicial.
6. **Qual é o resultado entregue?** Documento, projeto, acompanhamento, obra ou combinação desses elementos.
7. **Qual é o prazo indicativo?** Informar intervalo ou indicar que depende do escopo.
8. **Como é calculado o preço?** Área, complexidade, fase, visita, orçamento personalizado ou outro critério.
9. **Qual é a chamada para ação?** Pedido de orçamento, reunião, visita técnica ou envio de documentos.
10. **Existe um caso real associado?** Ligar o serviço a um projeto ou imagem autorizada sempre que possível.

### 2.4 Conteúdo recomendado para cada bloco de serviço

A versão final da página deve seguir uma estrutura repetível. Cada serviço deve apresentar um título claro, uma explicação curta, os principais entregáveis e uma ação seguinte. O texto deve evitar prometer aprovações, prazos ou resultados que dependam de entidades externas.

**Modelo editorial:**

> **[Nome do serviço]**  
> [Uma frase que explica o benefício principal para o cliente.]  
>  
> **Inclui:** [três a cinco entregáveis confirmados.]  
> **Ideal para:** [perfil de cliente ou situação.]  
> **Próximo passo:** [ação concreta para iniciar a conversa.]

## 3. Decisões prioritárias para a validação

A atualização do conteúdo deve começar pelos pontos que podem gerar contradições ou expectativas incorretas:

| Prioridade | Decisão | Motivo |
|---|---|---|
| Alta | Confirmar o número real de projetos em curso | O hero indica quatro projetos, enquanto a página lista cinco. |
| Alta | Confirmar o escopo de cada serviço | Evita publicar promessas que a equipa não consegue cumprir. |
| Alta | Confirmar contactos e prazo de resposta | Estes dados aparecem em chamadas comerciais e influenciam a conversão. |
| Alta | Definir a área geográfica de atuação | Alinha o posicionamento local com a ambição nacional. |
| Média | Confirmar a formulação oficial de missão, visão e valores | Garante que a nova secção representa a direção da empresa. |
| Média | Definir público prioritário | Permite escrever benefícios mais relevantes e chamadas mais eficazes. |
| Média | Reunir imagens e casos reais | Dá prova concreta aos serviços e aumenta a confiança. |
| Baixa | Decidir certificações, parceiros e número de colaboradores | Melhora a credibilidade, mas depende de autorização para publicação. |

## 4. Formulário de validação para a equipa

As respostas abaixo podem ser recolhidas numa reunião única com a administração ou com a pessoa responsável pelo conteúdo.

### Empresa

- Qual é o nome legal completo que deve aparecer no site?
- Qual é o ano de fundação?
- Em que localidades a JOCACH trabalha atualmente?
- Que localidades pretende servir nos próximos dois a três anos?
- Quais são os três principais tipos de cliente?
- Quais são os três maiores diferenciais da empresa?
- Existem licenças, certificações, registos ou parceiros que podem ser publicados?

### Missão, visão e valores

- A missão proposta descreve o trabalho real da empresa?
- A visão é local, provincial ou nacional?
- Quais são os quatro valores prioritários?
- Que comportamento ou exemplo real demonstra cada valor?
- Há palavras que a empresa prefere evitar, como “modernista”, “valorização” ou “referência”?

### Serviços

- Quais dos seis serviços publicados são efetivamente oferecidos hoje?
- Existem serviços que devem ser removidos, agrupados ou adicionados?
- Quem executa cada etapa: equipa própria, parceiros ou entidades externas?
- Quais são os documentos necessários para iniciar cada serviço?
- Quais são os entregáveis concretos?
- Quais são os prazos indicativos?
- Como deve ser solicitado o orçamento?
- Que projetos ou fotografias podem comprovar cada serviço?

### Contacto e conversão

- Quem recebe os pedidos enviados pelo site?
- Qual é o prazo real de resposta?
- O canal principal deve ser email, WhatsApp ou reunião?
- Deve existir uma visita técnica inicial?
- Que informação o cliente deve enviar para receber uma estimativa?

## 5. Próxima etapa de implementação

Depois de a equipa responder ao formulário, a atualização técnica deve ser dividida em três entregas pequenas:

1. **Conteúdo institucional:** atualizar nome, posicionamento, contactos, missão, visão, valores e indicadores do hero.
2. **Página de serviços:** rever os seis serviços, os entregáveis, o processo e as chamadas para ação.
3. **Consistência global:** substituir textos duplicados em cabeçalho, rodapé, página inicial, serviços, privacidade e metadados SEO.

A atualização deve ser feita numa nova branch e validada com `pnpm run check` e `pnpm run build` antes de abrir outro Pull Request.
